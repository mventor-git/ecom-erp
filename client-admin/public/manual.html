📖 Operator Manual — Ecom-ERP

The full path from a fresh install to daily business. No accounting knowledge needed. Arabic UI mirrors the same flows.

1First launch

  1. Backend: cd server && npm install && npm start — API on :5172. First run creates an empty database: no products, customers, reviews or transactions — only roles, permissions, Main Warehouse, price lists, chart of accounts and your operator account (from ADMIN_USERNAME / ADMIN_PASSWORD in server/.env).
  2. Admin panel: cd client-admin && npm install && npm run dev — :5174. Log in with the operator account. You land on Setup.
  3. Storefront: cd client && npm install && npm run dev — :5173.
A brand-new install is empty by design. Anything you see (products, badges, slides) means a previous session entered it — never demo data.

2The setup wizard (do this in order)

  1. Start your site — step 1 on the Setup page: company/store name, tagline, description. Every receipt, journal and the storefront reads it.
  2. Read this manual — you are here. Tick “I have read the manual” on the Setup page so the next steps unlock in order.
  3. Proceed — the wizard checklist, top to bottom: Currency & timezone (change BEFORE first data) → Warehouse (rename Main Warehouse, add shelves) → First financial period (required — postings and stock moves fail outside an open period) → Catalog (import or add products; stock comes later) → Suppliers / customers → Opening stock (counts shelves; each line posts a real movement + GL entry when costed).
The checklist is recomputed from your real records on every visit — it can never claim something that isn't true.

3Bringing data in (Setup → Import Data)

  1. Pick the dataset (Products, Suppliers, Customers, Warehouses) and Download template for exact columns.
  2. Upload CSV/XLSX → Preview: every line marked create / update / error with a reason; duplicates matched by business key (SKU→name, name, email, code); money must be plain amounts ≤ 2 decimals (stored as integer cents, never silently rounded).
  3. Commit (enabled only with 0 errors): one atomic transaction — one bad row aborts everything. Repeating an import updates matched records instead of duplicating.
Product imports never move stock. Inventory arrives only through receipts, opening balance, or counted adjustments.

4Purchasing: suppliers → PO → receive → payable

  1. Suppliers → create your supplier.
  2. Purchase orders → create (items at real supplier prices) → mark sent → confirmed (approval/rejection needs a reason and is audited).
  3. Receive goods → inventory moves AND the payable recognizes automatically: Dr Inventory / Cr Payables, line by line.
  4. Check AP Aging: recognition-date aging of open payables with control totals.

5Selling (every settlement posts journals)

ChannelHow it settles
Storefront / mobile orderOrder arrives unpaid. Cash collected via worker COD (auto-settles at delivery) or wire → settle with evidence (POST …/settle: method + reference + reason).
Counter sale (walk-in)Register page: validated price → stock issue + cash/revenue/COGS journal in ONE transaction.
Online payment (Kashier)Webhook settles atomically on provider confirmation.
You cannot type “paid” into an order status, on admin or worker. Money moves only through settlement — the slider refuses with SETTLEMENT_REQUIRED.

6Refunds vs goods returns (different things)

  1. Refund = money back: posts an immutable reversal entry. The original sale stays. Max one refund per order; partial refunds are refused (no domain truth yet).
  2. Goods return = stock back on the shelf: a counted correction/return movement (inspected OK). Never automatic with a refund.

7Paying suppliers

Supplier payments apply to purchase orders (full / partial / multi-PO, idempotent-safe): Dr Payables / Cr Cash. Posted payments are immutable — mistakes are corrected by reversal (opposite entry + status flip), never edit/delete. Record + reverse from the PO detail payables panel.

8Inventory (movements, not numbers)

  1. Stock is the result of movements (receipt, issue, adjustment, transfer, count, opening, return) — never type a quantity anywhere.
  2. Found damage/shrinkage while counting: adjustment (negative) with unit cost when known → books automatically (Dr Adjustments / Cr Inventory). Unknown cost stays listed in Inventory Recon — the system never guesses a number into your ledger.
  3. Transfers between warehouses/shelves move stock with no GL effect.

9Accounting (one journal, period locks)

  1. Chart of Accounts: your ledger skeleton (referenced accounts can't be deleted).
  2. Journals: every entry, its source, actor and timeline. Bridge journals are machine-owned and immutable; your corrections are manual journals (draft → post; unpost allowed with reason).
  3. Statements: Trial Balance, P&L, Balance Sheet — all computed from posted journals only. Dashboards stay explicitly operational.
  4. Periods: close to lock history. Closed periods fail CLOSED everywhere (settlements, reversals, adjustments, webhooks). Reopen is audited.

10Reconciliation controls (read these weekly)

ControlWhat it proves
AP AgingOpen payables = posted receipts − active payment applications, bucketed, with machine control totals.
Revenue ReconciliationOperationally-settled vs ledger-posted, per order, in 5 difference classes. Legacy “settled but unbooked” rows stay visible until you book-settle them — never auto-repaired.
Inventory ↔ GLWarehouse value vs ledger inventory, per movement, with idempotent catch-up posting.

11Team & permissions

One admin app for all employees. Create custom roles (driver, cashier, clerk…) and tick granular permissions — the interface adapts to what each user may touch. Money actions (orders.manage, journals.manage, settle/refund) stay with trusted roles only.

12Backup & recovery

  1. Database = server/data/store.db (+ 30 daily backups at 02:00). Full backup = copy the project folder.
  2. Restore = stop the API, swap the file back, restart. Never edit the live file by hand while the server runs.
  3. Rotate ADMIN_PASSWORD and webhook secrets before exposing anything publicly.

13Deliberate limits (honest, by design)

  • No supplier invoices / payment terms — AP ages from recognized receipts, not due dates.
  • No bank/transfer auto-posting, no cash-flow/VAT books, no retained-earnings closing.
  • No partial refunds, no goods-return-coupled refunds, no VIP on-bill receivables.
  • Mobile apps need LAN URL + Expo project setup; customer APK needs an Expo account.

14Troubleshooting

SymptomDo this
“Closed period” / settlement refusedPost into the open period, or reopen the period (audited) and retry.
Slider paid/refund refusedUse Settle (with evidence) / Refund seams — status can never carry money.
Import commit disabledFix every preview error row; one bad row blocks the whole file.
Product invisible in shopCheck active flag, stock on hand, and (if filtered) its category/brand.
Numbers look offOpen the three reconciliations (section 10) — the difference rows name the cause.
